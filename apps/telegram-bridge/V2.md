# Telegram mower connector

New installations opt into `LAUN_CONTROL_V2=true`. Existing v1 session routing
remains available with `false`. Both use grammY long polling; there are no
Telegram webhooks or public worker listeners.

Controller configuration:

- `LAUN_TELEGRAM_BOT_ID`: the numeric prefix of the bot token (or derive from
  `TELEGRAM_BOT_TOKEN` when that secret is intentionally present on controller).
- `TELEGRAM_ALLOWLIST_IDS`: permitted numeric user IDs. Empty means nobody.
- `TELEGRAM_ALLOWLIST_CHAT_IDS`: explicit negative group/forum chat IDs. Private
  chats are the default; a user allowlist alone does not authorize group output.
- `LAUN_TELEGRAM_BRIDGE_TOKEN`: optional distinct bridge credential; falls back
  to the existing service token. Keep it outside all mower sessions.

The bridge uses the same bridge credential, bot token and user allowlist, plus
`BRIDGE_DATA_DIR` for its durable inbox and `BRIDGE_INBOX_KEY` for stable
at-rest encryption. Use at least 32 random characters and back it up separately.
If no explicit encryption key is provided, it derives from the bot and bridge
credentials; drain the inbox before rotating those credentials. Missing or
incorrect encryption material fails startup and preserves ciphertext.
V2 bridge credentials use HTTPS outside loopback. An operator can explicitly set
`BRIDGE_ALLOW_INSECURE_NETWORK=true` for a separately trusted private HTTP
network; it defaults to false and never permits credentials embedded in a URL.
The supplied Compose stack opts in for its internal `http://gateway:8080`
service network. Public controller URLs should use HTTPS.

In the authenticated web app, generate a Telegram account link code. Send
`/link <code>` to the bot privately. Codes expire in two minutes, are stored only
hashed on the controller, and can be used once. Linking maps the verified
Telegram bot/user pair to the existing app owner. Before linking, only help and
linking are available; no separate invisible mower account is created. Changing
owners requires unlinking from the existing account first.

Commands:

```text
/new [mower name] | <goal>
/mowers
/thread [thread id]
/delegate [mower name] | <goal>
/status [thread id]
/approve <short handle>
/deny <short handle>
/deliveries
/retry <delivery id>
```

Without a mower name/separator, `/new <goal>` uses the existing director or
creates the groundskeeper. Plain messages append durable follow-ups to the
selected thread, even while it is busy. A route is the exact bot + chat + forum
topic + user tuple, including supported private-chat forum topics. Linking is
still private-chat only; a private topic does not grant group access. Selecting
another topic or sharing a group does not share
thread ownership. Delegating subscribes to the child while leaving the director
selected; use `/thread <child id>` to speak directly to it. Group participants
can see messages posted in their group, so only allowlist groups whose members
may see the work routed there.

This connector accepts text and exact permission callbacks. An edited message
does not replace, cancel or replay work already accepted from its original:
the bot queues an immutable-work notice and asks for a new message to redirect
the agent. Photos, documents, voice, stickers and other nontext content receive
text-only guidance. Their bodies/captions are not copied into an agent thread.
Attachment processing is not implemented. Commands addressed explicitly to a
different bot username are ignored rather than starting Laun work.

The bridge encrypts an incoming update in a local SQLite inbox before allowing
long polling to advance. Controller admission deduplicates the bot/update ID
and atomically writes the user action plus response outbox. Correcting a server
rejection can be followed by the explicit `TelegramInbox.retryRejected()`
operator action; rejected ciphertext is retained rather than silently submitted
under changed identity rules.
If private inbox admission fails, the grammY polling loop exits by throwing a
sanitized error. It deliberately avoids `Bot.stop()` on that path, because
grammY's stop routine acknowledges its last attempted update. After storage is
repaired and the bridge restarts, Telegram can redeliver that unacknowledged
update. There is no successful admission claim while local durable storage fails.

Output subscriptions and cursors live on the controller. Text is coalesced and
chunked below Telegram's message limit; previews do not trigger external link
fetches. Short opaque permission buttons bind owner, user/chat/topic, action and
expiry. Another participant cannot use a copied button. Allowing an action
requires a complete bounded action preview; larger or missing previews must be
reviewed in the web app. A decision records intent and still passes the current
server authority checks before execution.

Outbox polls lease messages. Telegram429 schedules a persisted delayed retry;
content stays ordered per route, so later answer chunks cannot overtake an
earlier pending, sending or uncertain chunk. Durable command/status/retry
acknowledgements can bypass blocked content so the user can reconcile delivery.
permanent rejection is `failed`. A network timeout may follow a committed send,
so it becomes `uncertain` rather than being blindly sent again. A vanished
bridge's expired sending lease also becomes uncertain. Delivery acknowledgements
are idempotent, but Telegram itself provides no general exactly-once send API.
Use `/deliveries` and explicitly `/retry` after checking whether the message
already exists. Human owners can inspect receipts through
`GET /api/v2/identity/telegram-deliveries`.

After local throttling, the bridge rechecks the exact delivery lease and current
owner/route/allowlist immediately before sending. Revoked or unverifiable routes
do not start a new send from that check. An external send already issued can
finish after revocation; unlinking cannot recall Telegram messages or establish
that an ambiguous network request was rolled back. Approval buttons are still
verified again against current owner and action authority.

Tests use real controller HTTP and fake Telegram delivery. They verify account
linking, allowlists, topic/user isolation, durable duplicate updates, callback
binding, controller/bridge restart, encrypted outage admission, delayed429 retry
and ambiguous-send containment. These tests do not contact a real bot account.
Actual grammY long polling against a fake local HTTP Telegram API also proves
failed admission is not acknowledged and is delivered again after restart.
Delivery tests cover unlink during throttling, pre-send controller failure,
credential redaction and ordered large-answer retry. Live Telegram account and
production network delivery qualification remains separate.
