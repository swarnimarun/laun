# Supported v2 permission boundaries

The controller checks every action against the thread's immutable profile assignment and every ancestor's ceiling. A grant or profile revision cannot override an explicit denial. Generic commands require `process.execute`, `workspace.read` and `workspace.write` for `workspace:own`, because an arbitrary shell can read and modify that entire workspace. Approving a command through another tool name does not bypass those checks. More granular argument/path restrictions on arbitrary shell commands are not implemented.

In isolated mode, OpenShell adds an enforced filesystem ceiling and denies **all generic command network egress**. A process inside the sandbox cannot use `curl`, child processes or a language runtime to bypass a denied network operation. A profile's `network.connect` allow does not open a socket from a generic command: supported network access runs through the central MCP broker, which separately checks the exact tool identity/schema and endpoint origin before resolving credentials or making a request.

Custom `OPENSHELL_V2_POLICY` files must retain this supported ceiling. They require hard Landlock enforcement, `include_workdir: false`, explicit empty `network_policies` and `network_middlewares`, and filesystem roots no broader than the runtime's default. Read-only runtime roots are `/usr`, `/lib`, `/bin`, `/etc`, `/opt/pi`, `/proc`, `/sys/fs/cgroup`, `/dev/urandom` and `/dev/random`; writable roots are `/workspace`, `/tmp` and `/dev/null`. The narrow cgroup root permits the resource enforcement probe, not writes to resource controllers. A custom file may narrow those roots, although removing required runtime paths can make the boundary probe or workload fail. Root execution, unsupported fields, duplicate YAML keys, traversal paths, custom network rules and middleware configurations fail closed.

This restriction is deliberate: Laun does not yet compile versioned per-thread permission rules into arbitrary OpenShell network policies. Operator-authored egress rules must not silently become a second permission authority. The legacy executor's independently configured policy format is separate from this v2 support boundary.

The supervisor validates and snapshots policy bytes into a private file before creating a guest. It records their SHA-256 in the guest's trusted creation labels and requires the same policy identity when reopening a retained guest. Changing even an otherwise valid policy does not silently reinterpret an existing sandbox. Guests created before this policy identity was recorded, or guests whose identity does not match, remain preserved and cannot reopen implicitly. Stop and reconcile them, inspect the server checkpoint and use a reviewed fresh placement, including a move to the same worker if appropriate. Never delete the only durable guest to bypass the check.

## Workload resource ceilings

Isolated guests request 2 CPUs and 1 GiB by default. Set `OPENSHELL_CPU_LIMIT` to 0.1–64 CPUs with millicpu precision and `OPENSHELL_MEMORY_MIB` to an integer from 64–65536 MiB to choose another bounded ceiling. These settings apply to both the controller's local isolated runtime and remote workers. They are supervisor configuration, not an agent-controlled tool argument.

The runtime passes explicit `--cpu` and `--memory` values, checks `openshell gateway info -o json`, binds the requested configuration into the retained guest's resource identity, and verifies the running guest's own cgroup-v2 `cpu.max` and `memory.max` before model/tool dispatch. Both must be finite, positive and within the requested limits. Available resource specification fields are checked too. Unreadable, missing, unlimited or excessive cgroup limits fail closed; the runtime does not automatically switch to trusted local execution.

OpenShell 0.1.8's gateway report can omit portable resource capability fields. That omission permits only the independent guest verification path; an explicit unsupported capability rejects admission before guest creation. Driver advertisements alone do not replace the cgroup probe. A machine without delegated CPU and memory controllers needs its host/driver configured before isolated work can start. Explicit trusted local mode remains a separate host trust choice.

Local qualification used OpenShell 0.1.8 and rootless Podman with the complete Pi agent image. The guest reported `cpu.max = 200000 100000` and `memory.max = 1073741824`, enforcing the 2 CPU/1 GiB default. File tools, a denied write outside the allowed roots, durable artifact export and restart deduplication passed through the real Pi Durable harness. This verifies that local driver/host combination; it does not certify a different VPS's resource delegation or kernel configuration.

Trusted local mode is an explicit host trust choice. It still checks tool admission through the controller, but a permitted generic command runs as the host user and its individual filesystem operations and sockets are not sandboxed. Use isolated mode when the workload needs an enforced host/filesystem/network boundary.

MCP tool permission is its own capability. An authorized remote tool can have external side effects; a local workspace rule does not describe every remote service's behavior. Review its exact discovered definition and reusable argument scope. The broker requires both the tool action and its endpoint connection to be authorized and does not retry uncertain mutating requests automatically.
