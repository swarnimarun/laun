# Laun control plane and delivery plan

Historical baseline audit and accepted design, 2026-11-14. The gaps and delivery slices below describe the v1 starting point. See [implementation](implementation.md) and [current acceptance status](../core-status.md) for completed behavior and remaining checks. This design alone does not certify a deployment. No Rust port is planned now; Bun and versioned JSON contracts remain the current implementation.

## Product model

A **mower** is a named durable agent identity, not a process, Telegram bot token, host, or conversation. A **thread** is its durable conversation; a **run** is a unit of work with one or more explicitly tracked attempts; a **task** is work that can be delegated across threads. A **yard** is an enrolled execution host. The **groundskeeper** is a director mower with explicit delegation capabilities, not an administrator by default. A **gatekeeper** is the permission adviser: it asks about intent and proposes profile changes, but cannot approve itself or modify enforcement. These are UI names; stable API names remain mower/thread/run/worker/profile.

Each mower gets its own assignment of an immutable, versioned permission profile. Users may reuse a profile version across mowers or explicitly copy/fork it. Editing a shared profile creates a version and does not silently grant existing mowers new permissions. A thread snapshots its assignment; each side effect rechecks current revocations. A director can create constrained children and hand off tasks only within both its granted delegation scope and the receiving mower's profile. Direct user interaction with a child does not reparent it or impersonate the director.

## Architecture and ownership

Keep a modular control service, an executor, and connector clients. On one VPS these can be compose services; on a workstation the control service can dispatch to a remote executor over a private tunnel. Later workers connect outbound, using unique scoped credentials and renewable leases. Neither remote scheduling nor a new credential implies trusting worker-provided principal IDs.

The server owns mower identities, thread routing, run state, permission versions, approval intents, task ownership, connector offsets and the audit trail. Pi owns model/tool conversation files through explicit session paths under a server-owned durable directory. Existing gateway index.json and Pi session files remain compatible. Control metadata can use a separate transactional store; do not repurpose the Pi transcript as the scheduler or auth database. Keep secrets in a credential store and pass references to control records; transcripts and events need redaction at ingestion because tool output itself can contain secrets.

Use existing packages/protocol as the only cross-service contract. Extend additively and introduce /v2 routes when semantics change. All requests need runtime validation, bounded sizes and deadlines, not TypeScript casts. Every resource read, log subscription, mutation, approval and connector action needs a server-derived principal and authorization. Current global agent keys remain a single-owner compatibility surface until explicit migration; they must not be described as tenant isolation.

## Durable work and delegation

Separate desired state from observations. Persist user intent and idempotency key before dispatch; lease a run with an increasing fencing generation. Only events from the current worker/run/generation can advance its state. Reconcile after restart with the executor before resuming. Lost transport means unknown outcome, not success or automatic replay. External side effects require deduplication where providers support it; otherwise interrupt for reconciliation. Do not promise exactly-once execution across arbitrary tools.

One thread has at most one active run. Follow-ups form a durable FIFO queue, with steer a separate explicit operation. Task delegation records parent task, caller principal, child thread, budget allocation and a deduplicated handoff ID. Bound ancestry depth, total children, parallel children, token/cost/elapsed budgets and event/message amplification. Parent completion, child failure and cancellation require explicit policies. Child execution does not depend on an SSE consumer remaining connected. A task has one owner at a time; handoff is atomic. Return structured results and artifact references, never implicitly share whole transcripts or credentials.

## Reviewable delivery slices

1. **Trust baseline.** Fail on corrupt durable state, validate external input, remove control credentials from agent environments, bind private ports, expose deployment settings accurately. Verify existing behavior with the test suite before architecture changes. Blocking checks: no forged runtime/path accepted, no inherited control token, no false resume success after a truncated stream.
2. **Permission kernel.** Add runtime-neutral capability/profile/request/decision contracts, a deterministic deny-first evaluator, immutable profile versions, revocation and one-shot approval binding. No LLM permission verdict can create authority. Start exact resource matching; broad shell strings are not a security boundary. Tests cover deny precedence, expired approvals, profile changes and cross-mower decisions.
3. **Durable control registry.** Named mower identities, yard enrollment/capability metadata and server-owned threads with migration from v1 sessions; idempotent creation and assignment history. A server restart must preserve all names, routing and profile bindings. New registry endpoints must enforce owner/resource ACLs from their first release. Recording a yard does not authorize remote execution before the dispatch slice.
4. **Pi harness and tools.** Pin a tested upstream Pi version, evaluate the experimental Pi Durable 1.5.2 adapter before designing a competing task scheduler, and implement an SDK/RPC adapter and capability negotiation, explicit session resume, real tool interception, deny on absent mediation. Preserve runtime-neutral gateway contracts and existing fallback only where it can satisfy requested guarantees. Pin OpenShell separately and prove real sandbox enforcement before deploy enables it.
5. **Worker dispatch and durability.** Enrollment, heartbeat, capacity, leases, run generation fencing, durable queue, reconnectable event sequence and reconciliation. Initially one worker/VPS. Test partitions and kill/restart at every dispatch/ack boundary before multi-VPS failover.
6. **MCP/plugins and permission adviser.** Broker MCP server identities, tool schemas, credential references, policy decisions and outbound calls. Auto mode can choose an allowed alternative, ask a question, propose a limited grant, or stop; a denied action cannot be retried through another tool/worker/child. Risky provider writes remain independently authorized. Verify a compromised plugin cannot read sibling credentials.
7. **Delegation and connectors.** Director/child tasks, bounded spawning, handoffs and direct child interaction; Telegram topic and DM routing, durable subscriptions, idempotent inbound delivery and an outbound outbox. Both web and Telegram show true enforcement/approval delivery status.
8. **Installation and operations.** Reproducible local/VPS install, doctor checks, TLS/private access, backup/restore, versioned upgrade/rollback, sandbox lifecycle reconciliation and retention. Run live tests against pinned Pi/OpenShell on disposable infrastructure before declaring unattended isolation supported.

Slices 1–3 may start while the later designs remain proposals. A passing unit test against a stub is not a sandbox or provider integration proof. Each slice must update the implementation ledger, include meaningful tests of its invariants and receive an independent review before landing. Use small JJ commits on harness-v2; preserve working v1 instead of deleting the validated base.

## Migration, compatibility and open decisions

Avoid an immediate Pi fork: first prove SDK integration, isolate Pi types inside executor and keep upstream upgrade tests. Fork only if an identified lifecycle/security limitation cannot be supplied through supported SDK/extensions. A Rust service can later implement the same versioned protocol and storage migrations.

Existing sessions become legacy threads with explicit single-owner access and no invented mower identity. Import is idempotent; retain original IDs and Pi paths. Enable v2 incrementally and never auto-assign broader permissions during migration. Back up index.json, event logs, Pi files, sandbox workspace volumes and control metadata as one quiesced or manifest-consistent snapshot. Restore tests must verify profile versions and credential references as well as conversation replay.

Future decision points: SQLite metadata vs extending atomic JSON (choose transactions before multiple writers); host sandbox storage/export capabilities; exact Pi supported version; trusted-local escape hatch UX; resource ACL identity mapping for Telegram; whether OpenShell can supply required broker provenance at the pinned version. Resolve through acceptance tests, not assumptions. Installation checks must run the packaged CLI outside its checkout and perform authenticated model/sandbox readiness checks; a public health response is insufficient.

## First permission-kernel implementation boundary

Implement a pure policy evaluator in packages/policy using contracts from packages/protocol. It accepts a trusted server-built action (principal, workspace, mower, thread, run, operation, exact resource and canonical argument digest), immutable profile and optional one-shot grant. It returns allow, deny or ask plus a stable reason. All actions require explicit rules; matching denies beat allows; missing rules deny. Profile modes isolated/manual/auto determine whether an explicit ask rule may open a request. In isolated mode ask becomes deny; auto mode still returns ask and delegates dialogue to the adviser. It never infers approval from model text or broad shell command patterns.

A one-shot grant binds action ID, principal, workspace/mower/thread/run, profile ID and version, operation, exact resource and argument digest, with a short expiration. The caller supplies current revocations and consumes a grant atomically with dispatch in a later broker transaction. The pure evaluator cannot guarantee single use or host enforcement; explicitly test and document this limitation. Child profiles can only reduce exact capability sets and autonomy; an ask parent rule cannot become a child allow rule. Denied parent rules must remain denied even with duplicate overlapping rules. An eventual child ask-to-allow grant must also pass ancestor approval/delegation and current revocation checks, rather than only this profile comparison. No wildcard matching or shell parsing in the initial kernel.

This first module is deliberately not exposed as an enforcement API until adapters mediate every actual side effect. Existing Pi bash/MCP/extension paths are not covered by adding a library. The implementation ledger must say so, and UI must never claim that selecting a profile isolates a v1 session.
